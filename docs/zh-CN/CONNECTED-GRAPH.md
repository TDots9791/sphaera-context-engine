# 关联图谱：代码、文档与项目上下文

状态：**对可在本地构建能力的描述，而非对已签名发行版的声明**。某功能是否存在于已安装的构建中，以签名的发行说明为准。下列数字针对特定语料与机器，并非通用保证。

## 为什么

一个项目需要以多种方式审视自身。代码回答“什么调用了什么”。文档回答“哪份协议的哪一条款对此作出规定”。项目上下文回答“我们为何如此决定、还有什么未决”。这三种视角结构不同，在检索时不应混合：把代码与文档合并到一个索引会可测量地降低相关性。因此 Sphaera 将三种取向分开保存，并以**边**而非合并索引来表达它们之间的关联。

## 三种取向

| 取向 | 节点 | 回答 |
|---|---|---|
| 代码 | 文件、符号、导入、调用 | 什么调用什么，变更会影响什么 |
| 文档 | 文档版本 → 片段（条款）→ 实体 | 哪份文档的哪一条款，同一事物还在何处出现 |
| 项目上下文 | 推理线索：问题、决定、事实、冲突、缺口 | 为何如此决定，还有什么未决，依据什么 |

每种取向独立查询，并保留各自指向来源的准确地址（locator）。

## 取向之间的边

关联以确定性方式构建，并携带证据——由哪个节点、依据什么信号、在哪个地址建立。

- **文档 ↔ 文档**——依据共同的标识性实体（协议或案件编号、发票、税号、规范引用）。同一编号出现在协议、发票和验收单中，就把这些文档相互关联，包括跨格式（PDF、DOCX、XLSX）。弱重合（共同的日期或金额）不视为关联，从而不产生虚假边。
- **文档 → 代码**——依据文档文本中对文件路径的明确提及。一份点名源文件的规范会与该代码节点关联，并保留片段的地址。以文件路径作为无歧义信号进行匹配；按函数名匹配则留待单独的精确度测量。
- **项目上下文 → 代码与文档**——推理步骤与其所依赖的节点关联：显式（智能体给出引用）与自动（步骤文本中提及代码路径或已存在的文档实体）。推理绝不创建新来源——它只引用已经从真实材料中提取的内容。

边的完整性由独立命令校验：指向已消失节点（文件被删除、图谱重建）的引用会被检出为悬挂，而不会被忽略。

## 以工作续接取代手写交接

对于多日、多步骤的任务，Sphaera 保留一份**推理骨架**，并按模型窗口紧凑交付：

1. 先是待解问题与缺口——需要关注的部分；
2. 然后是决定与冲突——已确定的部分；
3. 然后是事实与假设——支撑；
4. 每一项都带有所涉代码与文档的地址，使模型能够调取准确证据。

骨架按 token 预算裁剪，但绝不清空：即便窗口非常紧张，也至少保留一项以供续接。与手写交接文件不同，骨架会**自我失效**：当关联来源变化时，相关步骤被标记以待复核，因此过期是可见的而非无声的。

实际效果：小型本地模型（例如约 6–9B）凭带地址的骨架续接复杂任务，而非依赖整个既往对话。

## 边界与诚实

- 检索时刻意不混合取向：以此保持各自的相关性。
- 边依据可靠信号构建（共同的标识性实体、文件路径）；较不可靠的信号仅在语料上测量精确度后才加入。
- 项目上下文是派生层：它不改写源事实，也不创建来源。
- 性能与覆盖数字均为语料相关；方法与后续测量见[性能文档](PERFORMANCE.md)与[完整图谱报告契约](FULL-GRAPH-REPORT.md)。
